# SAT radar entry: OpenTelemetry

This is a scorecard evaluation, not an edit to the Universal Cake Evaluation Metrics document itself. It applies the v0.5.0 metrics to a specific candidate for the radar, using the Scorecard template from that document.

- **Product or service name:** OpenTelemetry
- **Version evaluated:** Project as of August 2026. Traces and metrics APIs are marked stable across major languages; logs is a newer, less mature signal. Specification and SDKs are versioned independently per language; see [status](https://opentelemetry.io/status/) for the current per-signal, per-language maturity matrix.
- **Evaluator:** Claude (Anthropic), drafted for Christopher Steel's review
- **Date:** 2026-08-21
- **Radar ring:** Assess (light pass, per v0.5.0 Lifecycle: all [GATE] criteria and the Security section covered; other rows covered where evidence was readily available, several remain Inferred or flagged Unknown rather than Verified)

## What it is

OpenTelemetry is an open source observability framework for cloud-native software: a single set of vendor-neutral APIs, SDKs, and a Collector service for capturing and exporting traces, metrics, and logs. It is a CNCF **Graduated** project, the foundation's highest maturity tier, formed from a 2019 merger of the OpenTracing and OpenCensus projects. This is developer infrastructure and a wire protocol (OTLP), not an end-user-facing product, which matters for how several rows below read.

## Bottom line for the radar

Nothing here blocks an Assess-to-Trial move. The two Moderate ratings (Environment, and Security's realized-vulnerability caveat) are both ordinary for the observability-tooling category rather than OpenTelemetry-specific weaknesses, and the Exit and portability gate, the item that most often kills a candidate outright, is not just a pass but close to the strongest possible case: the whole project exists to make vendor exit cheap for everyone downstream of it.

The one thing worth deciding before a Trial-ring evaluation: whether to benchmark the Environment and hardware/connectivity overhead rows directly (currently Inferred), since a project of this scale is a reasonable candidate for that closer look.

## Feedback for the framework

Two things surfaced while filling this out that are worth carrying back into the metrics document itself, separate from this scorecard:

1. **Accessibility and Interaction Patterns both assume an end-user-facing interaction surface.** For developer infrastructure or a protocol like this one, neither pillar has much to grip onto, and forcing an answer risks either an unearned Strong (nothing to fail) or an unfair Weak (nothing to point to as passing). A short note in the main document distinguishing "end-user product" from "developer infrastructure or protocol" evaluation profiles, and saying explicitly that Not applicable is a legitimate rating for some rows in the latter case, would help future evaluators avoid both failure modes.
2. **LFX Insights (added as Tooling in References in v0.4.0) worked exactly as intended here** — it turned two Market Position and Longevity questions that would otherwise have been Inferred guesses into Verified, dated figures within a couple of searches. Worth keeping in mind as a first stop for any other CNCF or Linux Foundation project that reaches the radar.
